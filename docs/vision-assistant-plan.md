# Лёгкая VLM для ровера: план передачи следующему агенту

Дата исследования: 2026-09-04. Статус: план, не реализованная функция.

## Запрос владельца

Ровер должен получать изображения со своей ESP32-CAM, описывать обстановку,
замечать людей, предметы и игрушечные дорожные знаки, затем озвучивать результат.
Это не только классификатор знаков. В перспективе нужны память о местности,
карта и поездка к выбранной точке. Управление сейчас преимущественно с iPhone.
Главный приоритет: скорость и устойчивость при нестабильном Wi-Fi.

Последнее уточнение владельца: основной путь должен быть с лёгкой LLM,
способной понимать изображения, если скорость окажется приемлемой.
Технически это VLM: визуальный энкодер плюс языковая модель, получающая
изображение и текстовый вопрос. Обычная текстовая LLM не читает JPEG сама.
ML является общим названием технологии; LLM/VLM не противоположность ML.
Основной результат этого плана именно свободное описание кадра через VLM,
а не замена его набором рамок и заранее написанных фраз.

Текущее поручение: исследовать, составить и опубликовать план. Реализация,
обучение моделей и физические испытания в это поручение не входят.
Следующему агенту сначала получить поручение на соответствующий этап.

Важная граница ожиданий: VLM описывает разные объекты и отношения между ними,
но не понимает буквально всё. Она может пропускать объекты, путать знаки,
выдумывать детали и неверно оценивать пространство. Описание кадра не является
картой, измерением расстояния или доказательством, что путь свободен.

## Оборудование и границы доступа

- Только наш ровер: шасси `192.168.2.23`, ранее наблюдались `car_id: 2`,
  `hostname: car-02`; камера `192.168.2.24`.
- IP сам по себе не является надёжным удостоверением устройства. Перед
  физическими тестами владелец подтверждает машину; сверить `/status`,
  ожидаемую идентичность и адрес камеры. При несовпадении не управлять.
- Не сканировать подсеть и не пробовать команды на других машинах.
- На момент передачи связи с ровером нет. Работать с сохранёнными кадрами
  и имитацией API до согласованных испытаний с владельцем.
- ESP32-CAM предоставляет JPEG через `/snapshot`; в спецификации также есть
  MJPEG на порту 81. Поворот камеры: `/servo`, фонарь: `/flash?v=0..255`.
- Веб-пульт в iPhone-ветке работает через `127.0.0.1:17777`, iPhone передаёт
  запросы по Wi-Fi. Не возвращать обход шлюза с Mac на адрес шасси.
- `/wheels` поддерживает ограниченный по времени импульс и автостоп;
  `/stop` останавливает движение. Сохранить интервалы запросов и существующий
  арбитраж режимов, не менять калибровку колёс в рамках зрения.
- В изученном API нет подтверждённых энкодеров, IMU и метрической одометрии.
  Сонар измеряет расстояние впереди, а не полный контур препятствий.
- Подтверждён только зуммер, не речевой динамик. Первая озвучка идёт с iPhone.
  Для речи из корпуса ровера потребуется отдельное исследование оборудования.

## Предлагаемая архитектура

```text
ESP32-CAM /snapshot -> один поставщик кадров на iPhone
                   -> предпросмотр
                   -> лёгкая VLM по запросу -> ответ о кадре -> речь iPhone
                   -> необязательный детектор -> объекты и короткие события

Ручное управление / сонар -> существующий контроллер движения -> шасси
                           (без зависимости от готовности ML)
```

Использовать именно камеру ровера. Камера iPhone не нужна для этой функции.
После предварительной загрузки моделей анализ и речь должны работать без
интернета. Локальный ML не устраняет задержку Wi-Fi между камерой и телефоном.
Запуск полноценной VLM на самой ESP32-CAM в этот план не входит.

Основной режим и возможное дополнение:

1. VLM: ответ на «Что видишь?» по свежему кадру, включая разные предметы
   и их взаимное расположение. Сначала только по кнопке или голосовому запросу;
   редкие автоматические описания добавить после замеров скорости и нагрева.
2. Необязательный быстрый детектор: известные классы и рамки, например человек
   слева. Добавлять при измеримой пользе, а не как обязательный шаг до VLM.
   Он не описывает всю сцену и не доказывает отсутствие препятствий.

Не обещать непрерывное понимание видео по анализу отдельных снимков.
Слежение за объектом во времени и память требуют отдельного состояния.

## Модели для сравнения

| Кандидат | Роль | Почему исследовать | Что ещё проверить |
| --- | --- | --- | --- |
| SmolVLM-256M-Instruct | Описание кадра и вопросы | Компактная VLM, 256M; карточка перечисляет описание, VQA и чтение текста | Рабочий iOS runtime, поддержка операций, память, русский язык и качество на ESP32 JPEG |
| FastVLM-0.5B | Альтернативная VLM | У Apple есть официальный пример локального приложения и Apple Silicon экспорты | Пример требует iOS 18.2+; проверить устройство, память, лицензии кода и весов, качество и время полного ответа |
| YOLO26n, экспорт Core ML | Необязательный детектор, не LLM | Поддерживается локальный Core ML; подходит для рамок объектов | Добавлять позже при необходимости; реальная скорость, классы и качество после квантования |

Источники: [SmolVLM](https://huggingface.co/HuggingFaceTB/SmolVLM-256M-Instruct),
[FastVLM](https://github.com/apple/ml-fastvlm),
[пример FastVLM для Apple](https://github.com/apple/ml-fastvlm/blob/main/app/README.md),
[YOLO Core ML](https://docs.ultralytics.com/integrations/coreml).

Предварительно: SmolVLM как компактный кандидат, FastVLM как кандидат с
официальным мобильным примером. Победителя выбрать по испытаниям, не по числу
параметров. Ни одна из моделей здесь не запускалась на телефоне владельца.
Не обещать готовый Core ML экспорт SmolVLM: сначала доказать совместимость
конкретной версии runtime и модели в небольшом автономном прототипе.

Не подключать дополнительно текстовую LLM к выходу VLM в первом прототипе:
сама VLM уже генерирует ответ, а второй генератор увеличит задержку и память.
Использовать один кадр, короткий запрос, ограниченный ответ и прогретую модель.
Не накапливать историю всей поездки в prompt: она увеличивает время и не
заменяет пространственную память. Ограничение токенов выбирать с проверкой
полноты фразы; показывать текст по мере генерации, но озвучивать законченное
короткое предложение. Отдельно учитывать TTFT и время завершения ответа.

Пример запроса для benchmark: "Describe the main visible objects and their
relative positions in one or two short sentences. Mention only what is
visible. If a detail is unclear, say so. Do not give driving instructions."
Это направляющая подсказка, не гарантия отсутствия выдумок. Сравнить также
русский запрос, не полагаясь на обещание многоязычности.

SmolVLM преимущественно англоязычна. Русское описание нужно отдельно оценить.
Если оно ненадёжно, согласовать локальную языковую обработку либо ограниченную
русскую озвучку проверенных классов. Не выдавать шаблон за свободное понимание
сцены и не подключать облачный перевод незаметно.

Базовый COCO-детектор имеет ограниченный набор классов, в том числе `person`,
`stop sign` и `traffic light`, но не весь набор дорожных знаков. Для конкретных
игрушечных знаков потребуется свой набор примеров и, вероятно, дообучение.
Источник: [COCO](https://docs.ultralytics.com/datasets/detect/coco).

При добавлении модели зафиксировать версию, источник, контрольную сумму весов,
препроцессинг, словарь классов, квантование и условия распространения.
Не коммитить большие веса в обычный Git. Загрузка заранее с проверкой целостности;
без модели показывать явное состояние, пульт при этом продолжает работать.

## Сеть, свежесть и приоритет управления

- Один источник кадров для предпросмотра и ML. Не открывать дополнительный
  поток и не дублировать загрузку одного снимка для каждого потребителя.
  Учесть и запросы через USB-шлюз, иначе веб-пульт создаст скрытую конкуренцию.
- Не отключать камеру или фонарь без действия пользователя. Допустимо
  адаптивно снижать частоту новых снимков; отображать паузу и возраст изображения.
- Не больше одного запроса снимка и одного inference каждого типа одновременно.
  Для ожидающих обработки кадров хранить только последний, не FIFO-очередь.
- Связать результат с `frameID`, поколением сессии и монотонным временем
  начала/окончания загрузки и обработки. После отмены, переподключения или
  смены режима поздний ответ не должен возвращать старое состояние.
- Время получения JPEG не равно времени экспозиции. Без метки камеры возраст
  кадра известен приблизительно: учитывать длительность запроса, запрещать
  HTTP-кэширование, отдельно проверять свежесть изображения в прошивке.
- Начальная гипотеза для эксперимента: 1 снимок/с, устаревание входного кадра
  через 2 с от начала запроса, ограничение генерации 40-60 токенами.
  Это настройки испытаний, не достигнутые показатели и не частота навигации.
- При плохой связи увеличивать паузы между снимками, не делать шквал повторов.
  Сначала измерить доступное разрешение и размер JPEG. Уменьшение картинки
  после получения на телефоне сокращает ML-нагрузку, но не Wi-Fi-трафик.
- Параметры качества JPEG и разрешения есть в драйвере ESP32, однако их
  изменение через API этой прошивки не подтверждено. Не выдумывать `/control`.
  Источник: [esp32-camera](https://github.com/espressif/esp32-camera).
- Декодирование, inference и загрузка модели вне главного UI-потока.
  Проверить, что используемый runtime поддерживает отмену либо поздний результат
  надёжно игнорируется. При перегреве и нехватке памяти отключается анализ,
  а не пульт. Не загружать несколько VLM одновременно в рабочем режиме.
- Стоп и моторный автостоп не ждут снимка, inference, синтеза речи или
  повторов сети. Сохранить исправления остановки из актуальной sonar-ветки.
- Если ровер двигался после снимка, не озвучивать результат как текущее
  положение вещей. Показать, что это описание предыдущего кадра; перед
  актуальным ответом запросить новый снимок. Не накапливать очередь озвучки.

## Контракт результата и ограничения действий

Проектируемый результат анализа содержит: `frameID`, поколение сессии,
временные метки, идентификатор модели, длительности, детекции с рамками,
отдельный текст VLM и состояние свежести/ошибки.

Численную уверенность детектора не смешивать с текстом VLM. Самооценка VLM
не является калиброванной вероятностью. Если нужен структурированный вывод,
валидировать схему и значения; невалидный ответ означает отказ, а не команду.

В первом релизе у анализатора нет доступа к `/wheels`, `/servo` или `/flash`.
Ни описание, ни текст в кадре не являются инструкцией к действию. Надпись
«езжай вперёд» на табличке или произнесённая самим приложением фраза не должна
запускать движение. Запретить произвольные URL и вызовы инструментов из VLM.

## Этапы и условия готовности

### 0. Уточнение платформы и набор испытаний

Узнать точную модель iPhone и iOS, доступную память/место, версию ESP32-платы,
размер и частоту JPEG, перечень игрушечных знаков. Получить с разрешения
владельца 30-50 кадров с камеры ровера: люди, разные предметы, несколько
объектов вместе, знаки, пустая сцена, размытие, темнота и частичные перекрытия.
Это стартовый оценочный набор, не достаточный обучающий датасет.

Разделять обучающие и тестовые записи по сценам/сессиям, а не соседним кадрам.
Кадры с людьми не публиковать в Git без отдельного согласия. По умолчанию
обработка в памяти, сохранение для тестов только явным действием.

Выход: инвентаризация устройства, размеченный оценочный набор и базовые
измерения пульта с камерой и без неё. Без ровера можно подготовить стенд
с ошибками API, но нельзя объявить скорость Wi-Fi проверенной.

### 1. Автономный benchmark моделей

На одном и том же iPhone и одинаковых кадрах сравнить обе VLM. Измерить
холодный запуск, подготовку кадра, первый токен и полный короткий ответ,
p50/p95, пик памяти, размер модели и нагрев за 10 минут.
Сначала проверить минимальную iOS/runtime. Не повышать deployment target
всего пульта ради модели без согласования; использовать доступность функции
по версии ОС или выбрать другой кандидат.

Предлагаемые ориентиры, не обещания: детектор p95 до 150 мс после декодирования;
полный VLM-ответ p95 до 3 с после декодирования на прогретой модели.
Отдельно измерить сквозное время от запроса снимка до начала речи.
Если VLM не укладывается, оставить её по запросу, а не задерживать управление.
Если даже ответ по запросу слишком медленный или неточный, не объявлять
проверку успешной: представить измерения и согласовать меньшую модель,
другое устройство или ограничение функции. Не подменять VLM детектором
без согласования и не переносить вычисления в облако автоматически.

На тестовом наборе вручную отметить правильность главных объектов, отношений,
ошибки/пропуски знаков и выдуманные объекты. Начальный ориентир: хотя бы
90% коротких описаний правильно называют основные видимые объекты;
ошибочные утверждения «путь свободен» недопустимы как основание движения.
Небольшой набор не доказывает безопасность. Результаты и примеры ошибок
оформить в benchmark-отчёт; решение о модели принимается после него.

### 2. Read-only зрение в приложении

Добавить общий поставщик кадров, абстракцию анализатора и режим «Что вижу»:
снимок, короткое описание VLM, возраст кадра, состояние модели.
Рамки детектора необязательны и не блокируют выпуск этого этапа.
Сохранить удобные телефонные портретный/альбомный режимы и доступный стоп.
Предусмотреть загрузку, отсутствие модели, отключённую функцию, разрыв связи,
устаревший результат, ошибку анализа и недостаток памяти.

Готовность: снимки обрабатываются именно с ESP32-CAM, без интернета после
загрузки весов; VLM отвечает о разных предметах, не только о дорожных знаках.
Все функции ручного пульта, сонара и фонаря сохранены.
Ни один исход анализа не отправляет команд движения.

### 3. Озвучка и голосовые команды

Локальная озвучка через `AVSpeechSynthesizer`, короткие ответы, возможность
прервать/выключить речь; проверить наличие нужного голоса без интернета.
Источник: [Apple Speech synthesis](https://developer.apple.com/documentation/avfoundation/speech-synthesis).

Распознавание сначала по удержанию кнопки микрофона, с явными разрешениями.
Для Apple Speech проверять `supportsOnDeviceRecognition` и требовать
`requiresOnDeviceRecognition`. Если язык/устройство не поддерживают офлайн,
показывать недоступность, а не молча использовать сервер. Альтернативу
whisper.cpp оценивать отдельно по памяти/скорости и поддержке русского.
Источники: [Apple Speech](https://developer.apple.com/documentation/speech/sfspeechrecognizer/supportsondevicerecognition),
[whisper.cpp](https://github.com/ggml-org/whisper.cpp).

Начать с команд описания и статуса. Движение голосом подключать отдельным
этапом: строгий список команд, явное включение режима, короткий импульс с
автостопом, без исполнения частичных гипотез, без повторного исполнения
одного распознавания и без свободной интерпретации моторных команд через LLM.
Не допускать управления от собственной речи приложения. Стоп доступен
физической кнопкой интерфейса независимо от микрофона и распознавания.

### 4. Игрушечные знаки

Собрать изображения реальных игрушек именно с ESP32-CAM на нужных дистанциях
и освещении; включить похожие знаки и отрицательные примеры. Дообучить
детектор/классификатор при необходимости. Измерить precision/recall каждого
класса и матрицу ошибок, отдельно после конвертации и квантования.
Не заявлять поддержку знака, которого не было в проверке. Маленький знак,
неразличимый в JPEG, не станет читаемым только от смены модели.

### 5. Карта и поездка к точке: отдельный проектный этап

Разделить семантическую память («видел стул») и геометрическую карту
с координатами, масштабом и оценкой ошибки положения ровера.
Подписи VLM не дают метрическую карту. Один обычный знак не уникален как место.

Для первой контролируемой трассы исследовать AprilTag-якоря с известными
размерами и положениями, только если владелец разрешит метки. Нужны калибровка
камеры, преобразование камера-корпус и учёт поворота камеры сервоприводом
либо её фиксированное положение. Метки дополняют понимание объектов,
а не заменяют пользовательскую задачу.
Источник: [AprilTag](https://github.com/AprilRobotics/apriltag).

Без меток отдельно исследовать visual SLAM и доступную одометрию/IMU.
Проверить пригодность частоты JPEG, размытия и сцепления колёс; не принимать
время подачи мощности за точное пройденное расстояние. ARKit ручного телефона
локализует телефон, а не удалённый ровер с ESP32-CAM.
Кандидат для исследования, не готовая iPhone-зависимость:
[ORB-SLAM3](https://github.com/UZ-SLAMLab/ORB_SLAM3).

Только после стабильной локализации: сохраняемая карта и маршрут, затем
выбор достижимой точки и движение с обратной связью. Нужны оценка препятствий,
ограничение скорости и остановка при потере положения, свежих данных или связи.
Начальные испытания на ограждённой трассе под наблюдением владельца.
VLM не заменяет навигационный контроллер и не доказывает безопасность пути.

## Обязательные проверки перед выпуском

- Fake API: таймауты, обрыв, поздние ответы, повреждённый JPEG, смена сессии,
  повторное нажатие анализа, остановка во время загрузки/генерации.
- Не растут очереди кадров, речи и движения; после отмены нет новых команд;
  анализ не возобновляет остановленный режим. Автостоп остаётся в командах.
- Включённая камера с анализом не ломает стоп и сонар. Замерить отдельно
  время UI -> отправка команды и UI -> подтверждение при одинаковых условиях.
  Ориентир: добавка p95 локальной задержки отправки не больше 50 мс;
  потерянный ответ не считать нулевой задержкой, отдельно считать таймауты.
- Офлайн-проверка: Wi-Fi ровера сохранён, интернет/сотовые данные недоступны,
  веса и голос уже загружены. Не должно быть скрытой облачной зависимости.
- Матрица реального устройства: портрет/альбом, фон/возврат, отказ микрофона,
  прерывание аудио, длительная работа, нагрев и ограниченная память.
- Сначала тесты со стендом без моторов, затем с разрешения владельца на
  подставке; испытания на полу только после проверки остановки и идентичности.

Существующие регрессионные проверки на актуальной iPhone-базе:

```bash
node --test tests/controller.test.cjs
swiftc -module-cache-path /tmp/rover-swift-cache \
  ios/RoverRelay/RoverCore.swift ios/Tests/main.swift \
  -o /tmp/rover-core-check
/tmp/rover-core-check
```

Добавить тесты новой логики отдельно. Эти проверки не заменяют полную сборку
Xcode и запуск на iPhone. В среде, где составлялся план, доступен только
Command Line Tools, поэтому работоспособность iOS/ML здесь не подтверждена.
